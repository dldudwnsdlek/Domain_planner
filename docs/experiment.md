## 해석

1. **정상 경로(S1~S9)에서는 세 구성이 똑같다.** 성공률 100%, LLM 호출 2.22회, Tool 호출 14.9회가 모두 같고 Worker LLM은 0회다. Planner·Worker 구조가 정상 요청에 비용을 더하지 않는다는 뜻이다(설계 목표 "Worker는 정상 경로에서 LLM 0회" 확인).
2. **복구가 필요한 경로(W1~W3)에서 차이가 난다.**
   - **A(단일 Agent)**: 집 좌표 없이 진행해 이동시간이 '판정 불가'가 되고, 재계획 사다리를 끝까지 돌다가 상한에 도달한다. 성공 22%, 평균 재계획 2.33회, Tool 55.8회로 가장 많은 호출을 쓰고도 결과가 없다. 성공한 2회(W1)는 분석 LLM이 실행에 따라 '근처'를 빼고 넘긴 경우로, 구조 덕분이 아니라 분석 결과가 우연히 깨끗했던 것이다.
   - **B(Worker LLM 끔)**: Worker가 규칙으로 Planner에게 넘기고, Planner가 바로 되묻는다. 헛된 재계획 0회, Tool 17회. 사용자가 한 번 더 답해야 하지만 실패는 없다.
   - **C(Worker LLM 켬)**: W1·W2는 Worker LLM이 '근처'·'우리 아파트'를 빼고 재시도해 **추가 질문 없이** 추천까지 끝낸다(자동 해결 6/6). W3('합정·망원 사이')는 추측하지 않고 되묻기를 골랐다(3/3). 대가는 W 요청당 LLM +0.89회, 응답 +2.3초.
3. **결론**: C를 기본 구성으로 쓴다. 정상 경로 비용은 A와 같고, 복구가 필요한 경우에만 LLM을 추가로 쓰며, 추측이 필요한 경우는 스스로 되묻는다. LLM을 쓰지 못하는 환경이면 B가 안전한 대안이다(실패 대신 되묻기).
4. **한계**: 응답 시간은 캐시를 채운 상태에서 쟀다(KOPIS 지연 제외). W 시나리오는 '분석은 통과하지만 카카오가 못 찾는' 실측 표현 3개뿐이라, 다른 유형의 실패(작품명 등)는 이 실험이 다루지 않는다. 분석 LLM이 temperature 없이 실행돼 같은 입력에도 추출 결과가 달라질 수 있다(A의 W1이 그 예).
